# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Marketing/info site for the NOSC-UA Digital Innovation Hub (DIH). Next.js 15.3 with the **Pages Router** for the public site, React 19, Tailwind CSS v4 and `next-intl`. Bilingual: Ukrainian (default) and English. News and the science categories (Biology, Ecology, High-energy physics) are managed in **Payload CMS 3**, which runs inside the same Next app (App Router, `/admin`) on Postgres.

## Commands

The package manager is **pnpm** (version pinned in `packageManager`). Copy `.env.example` to `.env` first.

```bash
pnpm db:up                       # start Postgres (docker, localhost:5434)
pnpm dev                         # dev server (Turbopack) on http://localhost:3000, admin at /admin
pnpm build                       # production build (standalone output)
pnpm exec tsc --noEmit           # type check (strict: false, strictNullChecks: false)
pnpm generate:types              # regenerate src/payload-types.ts after changing collections
pnpm generate:importmap          # regenerate the admin import map after adding admin components
pnpm migrate:create <name>       # create a migration in src/migrations after a schema change
```

There are no tests. ESLint is not installed, and `next.config.ts` skips linting during builds. Formatting follows `.prettierrc.json`: single quotes, JSX single quotes, trailing commas, `arrowParens: avoid`.

**Payload config changes need a dev server restart.** Payload caches its config, so edits to collections or hooks aren't picked up by HMR.

**Schema workflow.** In dev, Payload pushes schema changes to the local DB automatically. Production only applies migrations (`prodMigrations` in `payload.config.ts`, run on startup), so every collection or field change must ship with `pnpm migrate:create <name>` plus `pnpm generate:types`.

## Architecture

### Public site (Pages Router, `src/pages/`)
- `_app.tsx` wraps every page in `IntlProvider` (timeZone `Europe/Kyiv`) + `Navbar` + `Footer`.
- **i18n** uses Next's built-in `i18n` config, with locales `uk` (default, no URL prefix) and `en` (`/en/...`). Translations live in `src/messages/{uk,en}.json`, one namespace per page, and both files must keep the same keys.
  - **Every page must return `messages: (await import(\`@/messages/${locale}.json\`)).default` and `locale`** from `getStaticProps` or `getServerSideProps`. Without them, `useTranslations` breaks.
  - The App Router (Payload) ignores this config, which is why Next warns "i18n configuration is unsupported in App Router". That warning is expected.
- **CMS-backed pages** use `getServerSideProps`, so new posts show up immediately and builds don't need a DB:
  - `news/index.tsx`, `news/[slug]`
  - `science-services/[category]` and `[category]/[slug]`. Static siblings such as `eosc`, `egi` and `ung` take precedence over the dynamic route, and unknown categories return 404.
  - Data comes from `src/lib/posts.ts` (Payload Local API with `overrideAccess: false`, `locale` plus `fallbackLocale: 'uk'`). The UI lives in `src/components/posts/` (`PostList`, `PostView`, `PostHead` for OG tags, `RichText` for the Lexical → JSX converters; content styles are under `.rich-text` in `global.css`).
  - **Never import `src/lib/posts.ts` (or anything that imports `@payload-config`) from components.** It pulls `pg` and `sharp` into the client bundle. Client-safe helpers live in `src/lib/media.ts` and `src/lib/format.ts`.
- **Navbar**: the route list is hardcoded there. `getTextColor` keeps a `blackRoutes` list, and pages with a light hero must be added to it.
- **Styling**: Tailwind v4 is configured in CSS (`src/styles/theme.css` `@theme`), with no `tailwind.config`. Tokens: `blue-primary`, `blue-secondary`, `font-raleway`, `font-open-sans`. Images use plain `<img>` tags from `public/<page>/`.
- `src/constants/languages.ts` is unused leftover code. Ignore it.

### CMS (Payload, `src/payload.config.ts`, `src/cms/`, `src/app/(payload)/`)
- `src/app/(payload)/` holds the admin and REST routes generated by Payload. They are mostly boilerplate: don't edit them by hand, and regenerate `importMap.js` instead. GraphQL is disabled.
- **Collections:**
  - `Posts`: localized title, excerpt and Lexical content; `category` select; optional `cover` (falls back to `public/news/default-cover.webp`); `youtubeUrl`; `attachments`; slug; drafts with scheduled publish.
  - `Media`: uploads with webp sizes `thumbnail`, `card` and `large`.
  - `Users`: auth with a `role` field.
- **Categories are fixed in code** (`src/constants/postCategories.ts`, shared by the CMS and the pages). Adding a category means adding it there; science categories then get their page through the dynamic route, and the `ScienceServices` menu needs a link.
- **Roles:**
  - The first user created at `/admin` becomes `superadmin`.
  - Only a superadmin can create, update or delete other users and change roles.
  - An `admin` manages all content and can edit only their own account, not the role. The Users collection is hidden from admins.
  - Access functions live in `src/cms/access`.
- **Localization**: `uk` is required and `en` falls back to `uk`. `title`, `excerpt` and `content` aren't `required` at field level, because that would apply to every locale. Instead, the `requireUkrainian` hook in `Posts` enforces them when publishing in `uk`. An empty Lexical editor is stored as `null` so the fallback works.
- **`publishedAt`** is never entered by hand: a hook stamps it on first publish. Scheduled publishing runs through `jobs.autoRun` inside the app process.
- **Slugs** are auto-generated from the uk title with Ukrainian transliteration (`src/cms/utils/slugify.ts`).
- **Storage**: S3-compatible (Cloudflare R2) via `@payloadcms/storage-s3` when all `S3_*` vars are set, with keys under `S3_PREFIX`. Otherwise files go to `./media` on disk. Files are served through Payload at `/api/media/file/...`.
- **Startup**: `src/instrumentation.ts` boots Payload with the server. That applies migrations, seeds an empty install (`src/cms/seed`, only when there are no users and no posts) and starts the job runner.

## Deployment

`docker-compose.yml` runs `app` (container `dih`, port 3005) and `db` (Postgres 17, volume `pgdata`, published only on `127.0.0.1:5434`). The deploy workflow writes `.env` on the server from GitHub secrets. Inside compose, `DATABASE_URL` is overridden to point at the `db` host. `NEXT_PUBLIC_SERVER_URL` is a build arg, because it is inlined at build time.

On push to `master`, `.github/workflows/deploy.yml` SSHes to the server and runs `git pull`, `docker compose build app`, then `docker compose up -d`. A production build needs about 2.5 GB RAM; at runtime the app uses about 300 MB and Postgres about 50 MB. The `nginx` file is a reference config for the shared server.
